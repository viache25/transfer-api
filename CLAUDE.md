# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A REST API for account-to-account money transfers (Java 21, Spring Boot 4, PostgreSQL + Flyway). Portfolio pet project targeting the Vienna banking/fintech job market. The centerpiece feature is **idempotency**: a client (conceptually a POS terminal on a flaky network) retries `POST /transfers` with the same `Idempotency-Key` header, and the server must not double-charge.

The project is being built in three phases; check `git log` / current code state to see how far it's gotten before assuming a feature exists:
- **Phase 1 (core)** — skeleton entities/endpoints → idempotency + optimistic-lock retry + concurrency tests → Dockerfile/CI/README packaging.
- **Phase 2 (extensions)** — Redis idempotency cache + rate limiting, Spring Security, Actuator/Prometheus/Grafana, Testcontainers. Only after phase 1 ships.
- **Phase 3** — a C client simulating a POS terminal (HTTP retries reusing the same idempotency key). Only after phase 1 gets interview traction. Per D8 in issue #1 the C client is replaced by a Java + Toxiproxy network-failure test (plan step 20, done: `NetworkFailureIdempotencyApiTest`); the extension steps 17–24 (exact replay, REST Assured, PIT, Toxiproxy, k6, the `/ui` page, Playwright, ephemeral smoke test) are all done, and the plan in issue #1 is complete.

Explicitly out of scope: Kafka/RabbitMQ, microservices, a frontend (the one exception is D9's single server-rendered `/ui` test-target page, step 22), Kubernetes, multi-currency conversion, a custom auth server.

The step-by-step plan and its design decisions (D1, D2, …) live in GitHub Issue #1. Work happens in branches with one PR per change, merged only after CI is green; never push to `main` directly.

**Windows/Gradle gotcha on this machine**: the default `GRADLE_USER_HOME` (`C:\Users\<user>\.gradle`) contains Cyrillic characters, which breaks the forked test-worker JVM (`Could not find or load main class worker.org.gradle.process.internal.worker.GradleWorkerMain` — a JAR-manifest Class-Path encoding bug with non-ASCII paths). Work around it by pointing Gradle at an ASCII-only cache dir: `./gradlew test -g "D:/gradle-user-home"`. Only `test` (forked JVM workers) is affected; `compileJava`/`compileTestJava` work fine without the flag.

**Stack version note**: this project runs Spring Boot 4 / Spring Framework 7 / Jackson 3, which is newer than most published examples and tutorials assume. Notable breaking renames if something doesn't compile as expected: Jackson classes moved from `com.fasterxml.jackson.databind.*` to `tools.jackson.databind.*` (groupId `tools.jackson.core`); `@AutoConfigureMockMvc` moved from `org.springframework.boot.test.autoconfigure.web.servlet` to `org.springframework.boot.webmvc.test.autoconfigure`, and needs the `spring-boot-webmvc-test` test dependency (not bundled into `spring-boot-starter-test` the way it was in Boot 3). Don't assume Boot 3-era package names/artifacts — check the actual jar contents in `~/.gradle/caches` (or wherever `-g` points) if an import fails to resolve. Also: Hibernate 7 maps `java.time.Instant` to `TIMESTAMP_UTC` (`timestamp with time zone` on Postgres), so any timestamp column backing an `Instant` field must be `TIMESTAMPTZ` in the Flyway DDL or `ddl-auto=validate` aborts startup. `HttpStatus.UNPROCESSABLE_ENTITY` is deprecated in Spring 7 — use `UNPROCESSABLE_CONTENT`. Boot 4 also split `FlywayAutoConfiguration` out of `spring-boot-autoconfigure` into its own module — having `flyway-core` + `flyway-database-postgresql` on the classpath is not enough to trigger migrations at startup; the app also needs `implementation("org.springframework.boot:spring-boot-flyway")` (the same split pattern as `spring-boot-jdbc`/`spring-boot-jpa`/`spring-boot-hibernate`). Without it, Hibernate's `ddl-auto=validate` fails against an empty schema with `SchemaManagementException` because Flyway silently never ran — no error is logged about the missing autoconfiguration, so this is easy to misdiagnose as a schema/DDL bug.

The app needs a running Postgres to start (JPA `ddl-auto=validate`, schema owned by Flyway) or to run tests that load the Spring context:

```bash
docker compose up -d postgres redis
```

`docker compose up` starts the full stack: `postgres`, `redis`, `app` (built from the multi-stage `Dockerfile`, `dev` profile), `prometheus` and `grafana`. The Dockerfile's build stage runs only `./gradlew bootJar` — never `build`/`check`: since step 18 `check` depends on `apiTest` (and since step 23 on `uiTest`, which also downloads Chromium), so `build -x test` would still run the Testcontainers API tests, and there is no Docker daemon inside `docker build` (that broke CD after PR #26). `bootJar` also skips the `-plain.jar` that the `jar` task adds, so `COPY build/libs/*.jar app.jar` matches exactly one file. For a fast edit/run loop, start only `postgres` and run the app with `bootRun`.

## Architecture

Layered, single-module Gradle project under `com.slavaslava.transferapi`:

- `domain/` — JPA entities. `Account` holds `balance` + `@Version` (optimistic locking) and owns its own invariant checks (`debit()` throws `InsufficientFundsException` on insufficient balance rather than the service checking balances directly). `Transfer` records a completed transfer including its `idempotencyKey` (failed attempts roll back and leave no row — there is no persisted FAILED state). `Deposit` is the same idea for deposits: one row per idempotency-key'd deposit, used only for replay lookups (a header-less deposit never creates one — see below).
- `repository/` — plain Spring Data JPA repositories (`AccountRepository`, `TransferRepository`, `DepositRepository`). `TransferRepository.findByIdempotencyKey` / `DepositRepository.findByIdempotencyKey` are the lookup points for idempotent replay.
- `service/` — business logic split in two, for both transfers and deposits: `TransferTransactionExecutor.execute` is the `@Transactional` core flow (same-account check → load both accounts → currency-match check → `from.debit()` / `to.credit()` → persist `Transfer`), while `TransferService.createTransfer` orchestrates around it (replay lookup, retry loop, duplicate-key race handling) and is deliberately non-transactional — see below. `DepositTransactionExecutor` mirrors this for deposits (`execute` credits + persists a `Deposit` row, `executeWithoutIdempotency` credits only, no row); `AccountService.deposit` is the non-transactional orchestrator.
- `web/` — `@RestController`s (`AccountController`, `TransferController`). Thin — validation (`@Valid`) and request/response mapping only, no business logic. `web/ui/` holds the terminal page (`TerminalUiController`, `TransferForm`, `UiMessage`; see Terminal UI below).
- `dto/` — request/response records. Responses have static `from(entity)` factory methods.
- `exception/` — domain exceptions (`AccountNotFoundException`, `InsufficientFundsException`, `CurrencyMismatchException`, `SameAccountTransferException`) plus `GlobalExceptionHandler`, a `@RestControllerAdvice` that maps them to RFC 7807 `ProblemDetail` responses. Bean-validation errors (`@Valid` failures) get RFC 7807 responses for free via `spring.mvc.problemdetails.enabled=true` — no custom handler needed for those.
- `config/` — `SecurityConfig` (Spring Security filter chain), `ApiKeyAuthenticationFilter` (reads `X-API-Key`, looks up `Terminal` by SHA-256 hash), `ApiKeyHasher`, `RestAuthenticationEntryPoint` (401 as `ProblemDetail`, since Spring Security's filter runs before `GlobalExceptionHandler` gets a chance), `DevTerminalSeeder` (`@Profile("dev")` `CommandLineRunner` that seeds one terminal — see Authentication below), and `OpenApiConfig` (`@OpenAPIDefinition` + `@SecurityScheme` describing the `X-API-Key` header for springdoc — see below).

Schema is managed entirely by Flyway migrations in `src/main/resources/db/migration/` (`V1__init.sql`, `V2__terminals.sql`, `V3__deposits.sql`); Hibernate is set to `validate` only, never to auto-generate DDL.

**Authentication (implemented)**: every endpoint except `/actuator/health`, `/actuator/prometheus`, `/v3/api-docs/**` and `/swagger-ui/**` requires a valid `X-API-Key` header — enforced by `SecurityConfig`'s `SecurityFilterChain` (stateless, CSRF disabled, `httpBasic`/`formLogin` disabled since this API has no browser session or login form). The chain permits `DispatcherType.ERROR`: when a handler throws an exception nothing maps, the container forwards to `/error`, and the API-key filter (a `OncePerRequestFilter`) does not run again on that dispatch, so without the permit every unhandled 5xx was rendered as a misleading `401 Missing or invalid X-API-Key header` (found by the k6 load test, where a deadlock surfaced as 401). A direct `GET /error` is a REQUEST dispatch and still needs a key; `ApiKeySecurityIntegrationTest` covers both. `ApiKeyAuthenticationFilter` (a plain `OncePerRequestFilter`, added before `UsernamePasswordAuthenticationFilter`) hashes the header value with SHA-256 and looks it up in `TerminalRepository`; a match sets an authenticated `UsernamePasswordAuthenticationToken` in the `SecurityContext`, a miss leaves the request unauthenticated so `anyRequest().authenticated()` rejects it. `RestAuthenticationEntryPoint` renders the 401 as RFC 7807 JSON directly (Spring Security's `AuthenticationEntryPoint` runs in the filter chain, before `DispatcherServlet` — `GlobalExceptionHandler`'s `@RestControllerAdvice` never sees auth failures). `TransferApiApplication` excludes `UserDetailsServiceAutoConfiguration` (Boot 4.1 moved this class to `org.springframework.boot.security.autoconfigure`, not the old `org.springframework.boot.autoconfigure.security.servlet`) — without the exclusion, having `spring-boot-starter-security` on the classpath makes Boot autoconfigure an in-memory `user`/generated-password login that this API never uses, and logs a misleading "Using generated security password" warning on every boot. The `dev` Spring profile (active by default in `docker-compose.yml` via `SPRING_PROFILES_ACTIVE=dev`) seeds one `Terminal` with a fixed key (`DevTerminalSeeder.DEV_API_KEY`, currently `dev-local-terminal-key`) on startup so the README curl walkthrough and manual testing work without a provisioning step; this seeder never runs outside the `dev` profile. There is no terminal-provisioning API yet — inserting a `Terminal` row (name + SHA-256 hash of the raw key, via `ApiKeyHasher.sha256Hex`) is the only way to add one elsewhere.

**Idempotency and concurrency (implemented)**: `TransferService.createTransfer` first looks up the `Idempotency-Key` in `TransferRepository`; if found, it verifies the incoming payload matches the stored transfer (from/to/amount) — a match replays the stored result (controller returns 200 instead of 201), a mismatch throws `IdempotencyKeyReuseException` → 422. Otherwise it calls `TransferTransactionExecutor.execute` (the actual `@Transactional` debit/credit/save) in a retry loop of up to 3 attempts, retrying on any `ConcurrencyFailureException` — an `OptimisticLockingFailureException` (an account's `@Version` changed under it) or a `PessimisticLockingFailureException` such as `CannotAcquireLockException` for a PostgreSQL deadlock victim (`40P01`); in both cases the attempt's transaction rolled back completely — so each attempt reloads fresh account state. After the last attempt `GlobalExceptionHandler` maps any `ConcurrencyFailureException` to 409 Concurrent Modification. Deadlocks are also prevented at the source: `spring.jpa.properties.hibernate.order_updates=true` makes Hibernate flush entity updates sorted by primary key, so two opposite transfers (A→B, B→A) lock the two account rows in the same order. Without it Hibernate flushed in load order (`from` first), and the k6 load test hit 1–2 deadlocks per run; `TransferLockOrderIntegrationTest` pins the order (it holds a `FOR NO KEY UPDATE` lock on the higher id — `NO KEY` so the transfer's FK `KEY SHARE` lock on insert isn't blocked — and asserts with `NOWAIT` probes that the transfer already holds the lower id's row while it waits). `TransferService.createTransfer` is deliberately **not** `@Transactional` itself — each retry attempt needs its own transaction/persistence context, otherwise stale entity versions would just get retried against. If two requests race with the same brand-new idempotency key, the DB's unique constraint makes the loser's insert throw `DataIntegrityViolationException`, which is caught and turned into a re-query (with the same payload-match check) instead of an error. `TransferTransactionExecutor.execute` must stay `public` — Spring's proxy-based `@Transactional` silently no-ops on non-public methods. The `Idempotency-Key` header is validated `@NotBlank @Size(max = 255)` at the controller.

**API docs (implemented)**: `springdoc-openapi-starter-webmvc-ui` serves `/v3/api-docs` (JSON) and `/swagger-ui.html` (redirects to `/swagger-ui/index.html`); both are on `SecurityConfig`'s public-path list, so they're reachable without an `X-API-Key`. `config/OpenApiConfig` declares the `apiKey` security scheme (`X-API-Key` header) via `@SecurityScheme` and applies it globally via `@OpenAPIDefinition(security = ...)`, so every documented endpoint shows the header requirement without per-controller annotations. The project is on springdoc 3.x (the Spring Boot 4 line), bumped from 2.8.6 by Dependabot once 3.x was published.

**Deposit idempotency (implemented)**: `POST /accounts/{id}/deposit` takes an *optional* `Idempotency-Key` header (`@Size(max = 255)`; a blank header is treated as absent). Without a key, `AccountService.deposit` behaves exactly as before — `DepositTransactionExecutor.executeWithoutIdempotency` credits the account once, single attempt, no idempotency bookkeeping, so a deposit racing a transfer on the same account can still surface as 409 Concurrent Modification and a client retrying a timed-out request without a key can still double-credit (this remaining gap is the header-less path only — see D3 in issue #1). With a key, `AccountService.deposit` mirrors `TransferService.createTransfer`: replay lookup in `DepositRepository` with a payload check (accountId + amount; mismatch → `IdempotencyKeyReuseException` → 422), then `DepositTransactionExecutor.execute` (credit + persist a `Deposit` row) in a retry loop of up to 3 attempts on `ConcurrencyFailureException` (optimistic-lock conflict or lock failure), with the same duplicate-insert race recovery as transfers. `AccountService.deposit` is deliberately not `@Transactional` for the same reason `TransferService.createTransfer` isn't.

**Metrics (implemented)**: `spring-boot-starter-actuator` + `micrometer-registry-prometheus` expose `/actuator/health` and `/actuator/prometheus`; both are on `SecurityConfig`'s public-path list (no `X-API-Key`) since step 10's Prometheus scraper won't send one. `TransferService` is injected with a `MeterRegistry` and increments four counters: `transfers.created.count` on a fresh transfer, `transfers.replayed` on a successful idempotency-key replay (including the duplicate-insert race path), `transfers.lock_retries` each time a `ConcurrencyFailureException` (optimistic-lock conflict or deadlock) triggers another attempt, and `transfers.key_reuse_rejected` when a replayed key's payload doesn't match. Gotcha: the first counter is *not* named `transfers.created` — Micrometer's `PrometheusNamingConvention` treats a `.created` (or `.total`/`.bucket`/`.info`) name suffix as a reserved OpenMetrics word (meant for internal series-creation timestamps) and silently strips it, which collapsed the metric into the meaningless `transfers_total` on `/actuator/prometheus` instead of `transfers_created_total`; verified live via `curl .../actuator/prometheus` before and after the rename. The other three names don't hit a reserved suffix and render as expected (`transfers_replayed_total`, etc). Deposits have no counters yet — the acceptance criteria for this step only covered transfers.

**API tests (implemented)**: `src/apiTest/java/.../api/` is a separate Gradle source set (task `apiTest`, `shouldRunAfter(test)`, and `check` depends on it, so `build`/CI run it with no workflow change). `TransferApiTest` boots the app on a random port (`webEnvironment = RANDOM_PORT`, rate limit raised to 1000/s) with its own Testcontainers PostgreSQL + Redis (`ApiTestContainers`) and drives it with REST Assured 6 over real HTTP (8 tests: account create/get, transfer 201, replay 200, key reuse 422, 401, insufficient funds 409, pagination). `OpenApiContract` fetches `/v3/api-docs` and checks each success response: operation documented, every declared schema property present with a compatible JSON type (hand-rolled instead of swagger-request-validator, which targets OpenAPI 3.0 while springdoc 3 emits 3.1). Request bodies are plain JSON strings (REST Assured's object mapping would need Jackson 2). JaCoCo still measures only `test`; `finalizedBy(jacocoTestReport)` is attached to `test` alone. CI's JUnit publisher (`dorny/test-reporter`) reads `build/test-results/test/*.xml`, `build/test-results/apiTest/*.xml` and `build/test-results/uiTest/*.xml` (comma-separated `path`), so API and UI tests show up in the PR's "JUnit results" check too. All `Test` tasks log one line per test (`testLogging.events(passed, skipped, failed)`), so the CI log shows which tests ran.

**Network-failure test (implemented, step 20 / D8)**: `NetworkFailureIdempotencyApiTest` (apiTest, 1 test) shares the API tests' Spring context (same `@SpringBootTest` properties + `ApiTestContainers`, so the context cache reuses it) and is `@TestInstance(PER_CLASS)` so a non-static `@BeforeAll` can read `local.server.port`. Then it calls `Testcontainers.exposeHostPorts(port)` (this must come *before* the Toxiproxy container starts, otherwise it has no `host.testcontainers.internal`), starts `org.testcontainers.toxiproxy.ToxiproxyContainer` (`ghcr.io/shopify/toxiproxy:2.12.0`; the TC 2 `testcontainers-toxiproxy` module already brings `toxiproxy-java` 2.1.11, so there's no explicit client dependency) and creates proxy `0.0.0.0:8666 → host.testcontainers.internal:<port>`. The "terminal" is a JDK `HttpClient` (HTTP/1.1, a fresh client per attempt, and the JDK never auto-retries a POST). It posts through the proxy while a downstream `limit_data` toxic with **bytes = 1** is active. Don't use 0: Toxiproxy ≥ 2.x keeps limit_data state per link, and with 0 it closes the connection immediately, possibly before the request reaches the app. With 1 it closes only when the first response byte arrives, and the app writes the response only after the transaction committed, so the cut is always post-commit with no sleeps. The test asserts an `IOException` at the client and exactly one committed transfer (checked directly, bypassing the proxy). Then it removes the toxic, retries with the same key, and asserts `200` with the same id and balances 70/30.

**Mutation testing (implemented)**: the `info.solidsoft.pitest` plugin (`pitest {}` block in `build.gradle.kts`, JUnit 5 plugin 1.2.3) mutates `service.*` and `domain.*`; `targetTests` is limited to the Docker-free unit-test packages (`service`, `domain`, `dto`), so `./gradlew pitest` needs no Docker. Report: `build/reports/pitest/index.html`. Not wired into `check`; `.github/workflows/mutation.yml` runs it every Monday 03:00 UTC and on `workflow_dispatch`, writes the score to the job summary (parsed from `mutations.xml`) and uploads `build/reports/pitest/` as the `pitest-report` artifact. Score measured 2026-10-05 (run 37270441812, after the deadlock fix and the UI's `listNewestAccounts`): 82 mutants, 74 detected (72 killed + 2 timed out — removing `++failedAttempts` makes a retry loop endless) → mutation coverage 90%, test strength 100% (every mutant a unit test reaches is detected). The 8 unkilled mutants are NO_COVERAGE: getters plus `AccountService.getAccount` / `TransferService.listTransfers`, which only integration/API tests exercise (PIT runs only the unit tests). The one survivor of the first run (`Account.debit` boundary `<` → `<=`) is killed by `AccountTest.debitOfTheExactBalanceIsAllowedAndLeavesZero`. Update the README "Mutation testing" table when the score changes.

Integration tests (`@SpringBootTest`) start their own PostgreSQL 16 via Testcontainers — each such test class is annotated `@Import(TestcontainersConfiguration.class)`, which pulls in a `@ServiceConnection`-annotated `PostgreSQLContainer` bean from `src/test/java/.../TestcontainersConfiguration.java`; Spring Boot auto-configures the datasource from the container, overriding `application.properties`. `./gradlew test` needs Docker but no running Postgres (compose or otherwise). Note: this project is on Testcontainers 2.x (managed by the Spring Boot 4.1 BOM), which renamed Maven artifacts with a `testcontainers-` prefix (`org.testcontainers:testcontainers-junit-jupiter`, `org.testcontainers:testcontainers-postgresql` — the old unprefixed `org.testcontainers:junit-jupiter`/`postgresql` coordinates exist on Maven Central only as legacy 1.x releases and won't resolve a version from the BOM) and moved `PostgreSQLContainer` to package `org.testcontainers.postgresql` (the old `org.testcontainers.containers.PostgreSQLContainer` still exists but is deprecated); it also dropped the generic self-type parameter, so it's `PostgreSQLContainer`, not `PostgreSQLContainer<?>`.

**Redis idempotency cache (implemented, transfers only)**: `TransferReplayCache` (`service/`) is a read-through cache of the `TransferResponse` JSON in Redis (`StringRedisTemplate`, key `idempotency:transfer:<key>`, TTL 24h) in front of `TransferRepository.findByIdempotencyKey`. `TransferService.createTransfer` checks it first (payload check runs on the cached response, same 200 replay / 422 mismatch rules), falls back to the DB on a miss, and writes to it after the executor's transaction has committed and after a DB-side replay. Every Redis error (read, write, corrupt entry) is logged and swallowed — the DB stays the source of truth, so a Redis outage only costs latency. `spring.data.redis.timeout`/`connect-timeout` are 200ms so the fallback is quick, and `management.health.redis.enabled=false` keeps an optional cache from turning `/actuator/health` DOWN. Compose has a `redis` service the app waits on (`SPRING_DATA_REDIS_HOST=redis`). Deposits are not cached. Integration tests get Redis from a second `@ServiceConnection(name = "redis")` `GenericContainer` (`redis:7-alpine`) in `TestcontainersConfiguration`; `TransferReplayCacheIntegrationTest` proves a replay is answered from Redis by deleting the DB row first. Unit tests: `TransferReplayCacheTest` (round trip, miss, failing/corrupt Redis) and cache cases in `TransferServiceTest`.

**Prometheus + Grafana (implemented)**: `docker-compose.yml` adds `prometheus` (config `ops/prometheus.yml`, scrapes `app:8080/actuator/prometheus`, port 9090) and `grafana` (port 3000, anonymous admin; datasource and dashboard provisioned from `ops/grafana/`, dashboard JSON `ops/grafana/dashboards/transfer-api.json`). `management.metrics.distribution.percentiles-histogram.http.server.requests=true` publishes `http_server_requests_seconds_bucket` so the dashboard's p50/p95/p99 panels work.

**Exact replay and money scale (implemented)**: `Transfer`/`Deposit` truncate `createdAt` to microseconds (Postgres `timestamptz` precision) at construction, so the 201 built from the in-memory entity and a later 200 replay read from the DB serialize identically. `AccountResponse.balance` and `TransferResponse.amount` are normalised to two decimals in the record's compact constructor via `dto/Money` (so `0` → `0.00`, also for entries deserialized from the Redis cache). Tests: `ResponseScaleTest` (unit) and a byte-identical-replay case in `TransferIdempotencyIntegrationTest`.

**Rate limiting (implemented)**: `TerminalRateLimiter` (`config/`) keeps one Bucket4j token bucket (`com.bucket4j:bucket4j_jdk17-core`) per authenticated terminal name, capacity and refill both `app.rate-limit.requests-per-second` (default 20). `RateLimitFilter` is a plain `OncePerRequestFilter` added right after `ApiKeyAuthenticationFilter` in `SecurityConfig`'s chain (constructed there, not a `@Component`, so the servlet container doesn't register it a second time); it skips unauthenticated requests (public paths and bad keys — those are 401'd/served without a bucket) and answers an exhausted bucket with a 429 RFC 7807 `ProblemDetail` plus `Retry-After` (whole seconds, at least 1), rendered directly like the 401 since filters run before `GlobalExceptionHandler`. Deviation from D6: buckets are in-memory, i.e. the limit is per application instance, not shared through Redis — Bucket4j's Redis proxy manager needs a raw Lettuce client that Boot's Redis auto-configuration doesn't expose, and Redis is only an optional cache here. Tests: `TerminalRateLimiterTest`, `RateLimitFilterTest` (unit), `RateLimitIntegrationTest` (sets the limit to 1/s via `@SpringBootTest(properties = ...)`; each test uses its own terminal names because bucket state lives in the shared context).

**Smoke test (implemented, step 24 / D10)**: `scripts/smoke.sh` is a dependency-light (bash, curl, jq) HTTP smoke test against `BASE_URL` (default `http://localhost:8080`) with `API_KEY` (default: the dev key). It polls `/actuator/health` until UP (`HEALTH_TIMEOUT`, default 60s), then runs 7 checks: health, no key → 401 problem+json, two accounts → 201, transfer → 201 COMPLETED, same request + same key → 200 with the same id, balances 70/30 (moved once), same key + different amount → 422. It exits 1 at the first mismatch and prints the last response. Money is compared numerically with `jq -e` (`.balance == 70`), so the two-decimal formatting doesn't matter. `scripts/smoke-ephemeral.sh <image>` is the environment wrapper both workflows call. It runs `docker compose -f docker-compose.smoke.yml -p transfer-api-smoke up -d` (the image comes from `IMAGE`, host port from `SMOKE_PORT`, default 8080; no build, no volumes, and **no dev profile**). Then it waits for health (Flyway has created `terminals` by then), generates a key with `openssl rand`, masks it in Actions, and inserts its SHA-256 into `terminals` via `docker compose exec -T postgres psql`, the same procedure as README "Deploying to a server". Then it runs `smoke.sh`. An EXIT trap dumps the app logs on failure and always runs `down -v`. Health is polled from the host with curl rather than through a compose healthcheck, so the runtime image needs no HTTP client. `*.sh` files are forced to LF in `.gitattributes` (Windows checkouts would otherwise break them), and `scripts/` + `docker-compose.smoke.yml` are in `.dockerignore`. Note: CD pushes `latest` before the smoke job runs, so a failing smoke test marks the release red but doesn't un-publish it.

**Load test (implemented, step 21)**: `load/transfers.js` (k6, pinned to 2.3.0 in CI) runs a `constant-vus` scenario named `terminals`: one VU per virtual terminal, each with its own key from `API_KEYS` (comma-separated; falls back to the dev key). Keys matter because `TerminalRateLimiter` buckets by terminal *name*: `load/provision-terminals.sh N` inserts N terminals with unique names (`load-<batch>-<i>`) and SHA-256 key hashes into the compose Postgres via `docker compose exec -T postgres psql` (same procedure as `smoke-ephemeral.sh`) and prints the raw keys on stdout (everything else goes to stderr). Each VU paces itself (`PACING`, 0.1s) to stay under 20 req/s. `setup()` opens `ACCOUNTS` (20) accounts with 1,000,000.00 each, so no transfer can fail for insufficient funds and every non-2xx is a real error. Each iteration sends one transfer (0.01–20.00) with key `<runId>-t<vu>-<iteration>`. 20% are re-sent after the answer and must get 200 with the same id. 5% are sent twice at once via `http.batch` and must get at most one 201 and one id. Lost responses, 5xx, 409 `Concurrent Modification` and 429 are retried with the same key up to 3 sends. `setup()`/`teardown()` act as a client using `API_KEYS[0]` and wait out 429s (`responseCallback` marks 429 as expected there). `teardown()` reads every balance and the history (`GET /transfers?accountId=..&size=1000&sort=id,asc`; sorted by id so paging is stable) and reconciles: total conserved, every balance = opening + recorded transfers, no duplicate key, no foreign key. Conservation alone would not catch a double execution. Thresholds: `http_req_failed{scenario:terminals}` < 1%, `http_req_duration{scenario:terminals}` p95 < `P95_MS` (250), `idempotency_violations` == 0, `ledger_violations` == 0 (both counters get a 0 sample in `setup()` so the thresholds are always evaluated; `teardown()` also throws on a violation). `.github/workflows/load.yml` runs `docker compose up -d --build postgres redis app` (dev profile, no Prometheus/Grafana), provisions 10 keys (masked), runs `k6 run --summary-export build/reports/k6/summary.json` with the web-dashboard HTML export, writes a summary table to the job summary and uploads `build/reports/k6/` as `k6-report`. Triggers: Sundays 04:00 UTC, `workflow_dispatch` (inputs `terminals`, `duration`), and PRs touching `load/**` or the workflow. It is not a per-PR gate, because shared-runner latency is noisy. `load/` is in `.dockerignore`. Measured numbers live in `load/README.md` "Results".

**Terminal UI (implemented, step 22 / D9)**: `/ui` is one Thymeleaf page (`templates/ui/terminal.html`, `templates/ui/login.html`, `static/ui/ui.css`), with no JavaScript and no build tooling. It exists only as a target for UI tests. `TerminalUiController` (`@Hidden`, so springdoc leaves it out of `/v3/api-docs`) calls the same `AccountService`/`TransferService` as the REST controllers. The page shows `listNewestAccounts(50)` (newest first, so freshly created test accounts are always listed), a transfer form with a fresh UUID `Idempotency-Key` on every render, and the history of `?accountId=` (20 newest). Posts to `/ui/transfers` follow post/redirect/get. The outcome travels as flash attributes: `result` (`TransferCreationResult`, rendered as `Created (201)` / `Replayed (200)` plus the id), `error` (`UiMessage` title/detail; the controller maps the same domain exceptions `GlobalExceptionHandler` maps and rethrows anything else), and `last` (the submitted form, rendered as a hidden-field **Retry with the same key** form; not set on bean-validation errors). Templates call record accessors as methods (`${result.transfer().id()}`), which works regardless of SpEL's record-property support. Stable `data-testid` attributes are there for Playwright.

Auth: a browser can't send `X-API-Key`, so `SecurityConfig.uiSecurityFilterChain` (`@Order(1)`, `securityMatcher("/ui/**")`; the API chain is `@Order(2)` and matches the rest) uses `formLogin` with `loginPage("/ui/login")` and `passwordParameter("apiKey")`. The form has no username field, so the key travels only as the credentials, which Spring Security erases after authentication. `TerminalApiKeyAuthenticationProvider` (wired via `authenticationManager(new ProviderManager(...))`, not a bean) does the same SHA-256 lookup as `ApiKeyAuthenticationFilter` and builds the same `ROLE_TERMINAL` authentication (`ApiKeyAuthenticationFilter.authenticated(Terminal)`). The terminal is then kept in the HTTP session: the session id is changed on login, and the cookie is HttpOnly with `server.servlet.session.cookie.same-site=strict` (set `...cookie.secure=true` behind TLS). CSRF stays on for this chain: Thymeleaf's `th:action` forms get the `_csrf` field automatically, and logout is `POST /ui/logout`. A CSP header (`default-src 'none'; style-src 'self'; img-src 'self' data:; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`) allows no scripts and no inline styles, so keep styling in `ui.css`. `/ui/ui.css` is public. The UI is not rate limited, and an `X-API-Key` header does not open it. The JSON API chain is untouched (stateless, header only), so a UI session can't call the API. Tests: `web/ui/TerminalUiControllerTest` (16 unit tests, standalone MockMvc with a hand-built `SpringTemplateEngine`/`ThymeleafViewResolver` and mocked services, so it renders the real templates without Docker) and `TerminalUiIntegrationTest` (11 integration tests with the real chain: login/session, bad key, CSRF 403, CSP, transfer, same-key retry → same id and money moved once, insufficient funds message, history, logout).

**UI tests (implemented, step 23)**: `src/uiTest/java/.../ui/` is a third test source set like `apiTest` (configurations extend `testImplementation`, plus `com.microsoft.playwright:playwright` 1.63.0). Task `uiTest` has `shouldRunAfter(apiTest)` and `dependsOn(playwrightInstall)`, and `check` depends on it, so `build`/CI/nightly run it. `playwrightInstall` is a `JavaExec` of `com.microsoft.playwright.CLI`: `install chromium`, plus `--with-deps` when the `CI` env var is set, so GitHub runners also get Chromium's OS libraries via `sudo apt`. It is a quick no-op once the browser sits in `~/.cache/ms-playwright`. `uiTest` sets `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`, so `Playwright.create()` doesn't fetch every browser, and passes `-Dplaywright.reports=build/reports/playwright`. `TerminalUiTest` (4 tests) boots the app with `RANDOM_PORT` and its own `UiTestContainers` (PostgreSQL + Redis), seeds a terminal via `TerminalRepository` and accounts via `AccountRepository`, and drives `/ui` in headless Chromium using the page's `data-testid`s: sign in, transfer → `Created (201)` + id + balances + history row, **Retry with the same key** → `Replayed (200)` with the same id/key and balances moved once, insufficient funds → error message, wrong key → "Unknown API key.". One `Playwright`/`Browser` per class; a fresh `BrowserContext` per test with tracing on. A `@RegisterExtension` `AfterTestExecutionCallback` runs before `@AfterEach` closes the context. On failure it writes `<test>.png` (full page) and `<test>-trace.zip` to `build/reports/playwright/`; on success it discards the trace. ci.yml uploads that directory, and it was proven once on PR #35 with a deliberately failing assertion. Spring Security 7 redirects to the *relative* `/ui/login`. Assertions use Playwright's auto-waiting `PlaywrightAssertions.assertThat`. The Docker image is unaffected: its build stage runs only `bootJar`, and the `dependencies` warm-up only resolves metadata.
